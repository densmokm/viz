Analytics across the deal lifecycle

Working demonstrations of what data and analytics contributes at each stage of a transaction — from finding the target to owning the asset. Every one runs on synthetic data, with the analytical logic as runnable code rather than a slide.

    How these are built

    House rules

    • Synthetic, but honest. Generators model the underlying drivers — cost indices, churn hazards, contractual terms, integration disruption — and the analysis then discovers the answer from the records. Nothing is hard-coded to produce a punchy finding, which is why the same code would run against a real extract.
    • It has to tie. Where an analysis decomposes a movement, the components reconcile exactly, and the reconciliation is asserted in code. A demo that fails its own checks fails loudly rather than publishing a number.
    • Fitted, not asserted. Where something is scored or predicted, the weights come from data. A hand-weighted index does not survive the first partner who asks where the numbers came from.
    • Built for the room. Each one answers the same five questions: what it is, what data it needs, how the calculation works, what the output looks like, and what a deal team does with it on Monday.

    What each demo contains

    • A seeded synthetic dataset with a generator you can re-run and change.
    • The analytical logic as commented Python, including the checks it has to pass.
    • An interactive page built on a shared chart toolkit — one scale per plot, no dual axes, a colourblind-validated palette, a table view behind every chart, and both themes designed rather than inverted.
    • A written note covering the ingredients, the arithmetic, and the "so what".

    The demos share one stylesheet and one chart toolkit, so a fix to a scale or a mark specification lands everywhere at once. That is the same argument for repeatable analysis packs on live deals — and the reason it is worth making structurally rather than promising it.
